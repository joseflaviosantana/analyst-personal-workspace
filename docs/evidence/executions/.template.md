## 4. Taxonomias Normativas de Referência

### 4.1. Taxonomia de Falhas (`failure_type`)
| Valor | Descrição |
| :--- | :--- |
| `SYNTAX_LINT` | Erros de sintaxe ou violações de regras estáticas de linting (`eslint`). |
| `TYPECHECK` | Erros de compilação ou inconsistências de tipagem estrita no TypeScript (`tsc`). |
| `TEST_ASSERTION` | Quebra de asserção em testes unitários, integração ou E2E (divergência esperado vs obtido). |
| `CONCURRENCY_IO` | Problemas de concorrência, locks de arquivo SQLite ou contenção de I/O em Windows. |
| `REGRESSION` | Comportamento ou contrato anteriormente válido que foi quebrado por alteração posterior. |
| `SPEC_MISMATCH` | Divergência funcional entre a implementação e os documentos normativos do produto. |
| `ENVIRONMENT` | Problemas de ambiente de execução (portas ocupadas, caminhos de arquivo, variáveis). |
| `NONE` | Execução bem-sucedida sem falha (e.g. homologação de novo Golden Flow canônico). |

### 4.2. Estágio da Falha (`failure_stage`)
| Valor | Descrição |
| :--- | :--- |
| `PLANNING` | Falha identificada na fase de compreensão, delimitação de escopo ou Gate 1. |
| `IMPLEMENTATION` | Falha identificada durante a escrita de código antes da verificação formal. |
| `STATIC_ANALYSIS` | Falha capturada pelo `npm run check:static` (`eslint` / `tsc`). |
| `UNIT_TEST` | Falha detectada durante a execução da suíte unitária (`vitest`). |
| `INTEGRATION_TEST` | Falha detectada durante a execução da suíte de integração com banco/regras. |
| `E2E_TEST` | Falha detectada nos testes end-to-end com Playwright. |
| `HYGIENE_AUDIT` | Bloqueio gerado pelo `scripts/audit-hygiene.mjs` (segredos, arquivos proibidos, diff). |
| `HOMOLOGATION` | Rejeição ou solicitação de ajuste feita pelo usuário no Gate 2. |

### 4.3. Classificação de Reutilização (`candidate_type`)
| Valor | Descrição | Regra de Promoção |
| :--- | :--- | :--- |
| `SKILL` | Procedimento ou padrão operacional reutilizável para colaboração Humano-IA. | **Nunca criar automaticamente**. Requer repetição comprovada e autorização humana explícita. |
| `SCRIPT_RULE` | Nova verificação estática, script determinístico ou regra de higiene do repositório. | Promovível via PR/commit pontual no diretório `scripts/` após validação. |
| `TEST` | Teste automatizado de regressão incorporado à suíte permanente de testes. | Adicionado diretamente em `tests/unit` ou `tests/integration`. |
| `TEMPLATE` | Modelo estruturado de código, documentação, especificação ou contrato. | Arquivado sob `docs/` ou pasta correspondente de arquitetura. |
| `COMPONENT` | Componente de interface, hook ou função utilitária pura de domínio. | Integrado a `src/core` ou `src/components`. |
| `GOLDEN_FLOW` | Fluxo canônico integral representativo de invariante arquitetural de referência. | Anotado com tag `[@golden-flow]` ou `[@golden-test]`. |
| `NONE` | Correção pontual, ajuste idiossincrático ou tarefa sem valor de reuso futuro. | Não gera artefato permanente de aprendizado. |

### 4.4. Vocabulário Controlado de Capabilities (`capabilities`)
| Identificador | Descrição Operacional |
| :--- | :--- |
| `CODE_INSPECTION` | Leitura, mapeamento estrutural e diagnóstico estático de código e documentos. |
| `SCHEMA_EVOLUTION` | Alterações e migrações estruturais de banco de dados e modelos Drizzle. |
| `TEST_ENGINEERING` | Autoria, refatoração, correção e execução de suites de testes (Vitest / Playwright). |
| `STATIC_ANALYSIS_FIX` | Resolução de erros de compilação TypeScript e conformidade com linter. |
| `DOMAIN_MODELING` | Implementação de entidades, regras puras de negócio e motores de transição. |
| `ANALYTICAL_ENGINEERING`| Desenvolvimento de regras analíticas de BI, DAX, Power Query M e conciliação numérica. |
| `HYGIENE_COMPLIANCE` | Auditoria de segurança, erradicação de credenciais e saneamento da working tree. |
